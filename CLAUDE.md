# GPT Caddy

Local FastAPI app for launching and monitoring micro-GPT training runs on RunPod GPU pods (container images built from `pod-image/`).

## Pod image build

The RunPod container images live in `pod-image/` (a self-contained Docker build context; build via `pod-image/build.sh`). Three layered images, all `ghcr.io/sysreq/`:
- `gpt-caddy-base` (`Dockerfile.base`) — Ubuntu 26.04 + baked torch/CUDA venv, split across layers for parallel cold-pull. Rebuilt rarely.
- `gpt-caddy-single-train` (`Dockerfile`) — `FROM` base; GPT Caddy's default launch image (`config.DEFAULT_IMAGE` / `TEMPLATE_NAME`). Its entrypoint `scripts/bootstrap.sh` git-clones gpt-golf at boot and runs `train_gpt.py` — the training code is **not** baked in.
- `gpt-caddy-cache-server` (`Dockerfile.redis`) — `FROM` base + `redis-server`; the shared torch.compile (Inductor) cache. GPT Caddy finds it via `runpod/cli.detect_redis_server` (matches `cache-server` in the image name).

The train image bakes only gpt-golf's **dependency closure** so the pod's runtime `uv sync` is a no-op. That closure is gpt-golf's `pyproject.toml` + `uv.lock` (torch/flash-attn/CUDA), **not** GPT Caddy's own root manifest — so `pod-image/` keeps a **vendored copy** of gpt-golf's manifest that `build.sh` refreshes from the gpt-golf checkout before building (override location with `GPT_GOLF_DIR`). `scripts/discover_cache.sh` is not baked — it runs on the pod from the cloned gpt-golf repo. Renaming any image means updating both `build.sh` and the three `config.py`/`cli.py` references above. See `pod-image/README.md`.

## Event pipeline

Pod-side daemon (`gpt-golf/scripts/pod_eventd.py`) serves structured JSONL events + the raw log → `PodPoller` (podterm/events.py) pulls via the RunPod HTTP proxy (`https://{pod_id}-8765.proxy.runpod.net`, bearer token from the per-launch `EVENTD_TOKEN` env, persisted in the run's `config_json`) → the thread-safe queue owned by `EventPipeline` (podterm/pipeline.py) → its `drain_loop` → SSE fan-out via `SSEHub` (podterm/sse.py) to the web UI (static/index.html) + SQLite (podterm/db.py).

- Module layout: `server.py` is glue only (FastAPI app, lifespan, static, router mounts). Logic lives in `pipeline.py` (event drain + telemetry, `EventPipeline`), `sse.py` (fan-out, `SSEHub`), `pods.py` (pod lifecycle + poller registry, `PodManager`, plus `LaunchConfig`), `routes/` (thin `APIRouter`s), `models.py` (event dataclasses), and the `runpod/` package. Service objects are module singletons (`pipeline`, `hub`, `manager`); DAG is `SSEHub` ← `EventPipeline` ← `PodManager`.
- The live path consumes structured events only (via `EventPipeline`). Keep the event schema in sync with the producers in gpt-golf (`bootstrap.sh` `emit`, `train_gpt.py` `emit_event`) — schema changes need a gpt-golf image rebuild + push.
- The phase strings `"Starting Training"` and `"Training finished"` are load-bearing in `EventPipeline.drain_loop` (podterm/pipeline.py) and the UI.
- All RunPod interaction goes through the `runpodctl` CLI (podterm/runpod/cli.py), with two sanctioned exceptions, both read-only and confined to podterm/runpod/api.py: `api_get_telemetry()` (GraphQL `myself.pods.runtime` — runpodctl exposes no utilization fields) and `api_get_machine_logs()` (`hapi.runpod.net/v1/pod/{id}/logs` — host-level boot/image-pull lines that predate the container). Keep any future direct API use confined to that package too. The `podterm.runpod` package re-exports the public surface, so callers import from `podterm.runpod` unchanged.
- The hapi logs endpoint does NOT accept the RunPod API key (403). It needs a short-lived (~60s) Clerk *console* JWT, which `podterm/runpod/console.py` mints on demand from the user's `__client` cookie (`RUNPOD_CONSOLE_CLIENT_COOKIE` in a gitignored `.env`, loaded by `config.load_dotenv()` at startup). All best-effort: no cookie → boot panel just never appears. Full auth notes in the project memory (`hapi-logs-auth`).
- Before the event daemon is reachable, `PodPoller` polls machine logs and emits `t: "pull"` events (parsed by podterm/boot.py `PullTracker`); the UI shows only the boot panel until the container is up (`isBooting` in static/js/live.js).

## Off-pod model-health diagnostics

The diagnostics suite (runtime model-anatomy probe + self-verifying forward pass + per-family metric stages, schema-v2 JSON) lives in `podterm/diagnostics/` — it was moved here from gpt-golf so all the diagnostics code has one home. Training no longer runs it on the pod; GPT Caddy runs it locally on snapshots, off the training GPU.

- Producer (gpt-golf): `train_gpt.save_snapshot()` writes a step-tagged `state_dict` to `$SNAPSHOT_DIR` (`/workspace/snapshots`, outside the repo) and emits a `t: "snapshot"` event (`step`, `file`, `bytes`, `sha256`, `final`) every `TRAIN.snapshot_every` steps and once at the end. The daemon serves it at `GET /snapshot?step=N`; `GET /snapshot/ack?step=N` writes the teardown-handshake sentinel. ValBPB stays on the pod (the `summary` event from the normal eval path).
- Consumer (GPT Caddy): `drain_loop` routes `t: "snapshot"` → `snapshots.handle_snapshot` (podterm/snapshots.py), which downloads the checkpoint (same bearer/proxy channel as `PodPoller`), runs the suite as a **subprocess** (`python -m podterm.diagnostics`) under **gpt-golf's torch env** (`cwd=GPT_GOLF_DIR`, podterm root on `PYTHONPATH`), persists the JSON to the `run_diagnostics` table (`db.add_diagnostics`), and fans out a `diagnostic` SSE event (carrying the `health` block). On the `final` snapshot it calls `/snapshot/ack` to release the pod (bootstrap.sh's `cleanup()` waits ~120s for it on success). Per-pod processing is serialized + coalesced to the newest pending snapshot.
- Health verdict: `podterm/diagnostics/health.py` (**stdlib-only**, importable in both envs) owns the curated `HEADLINE` metric registry, per-metric good/warn/bad threshold bands, and the overall verdict (worst of section-execution statuses and metric bands). `runner.py` computes it once and writes top-level `status` + `health` into the doc; `snapshots.py` reads `diag["status"]` (falling back to the execution-only `_overall_status` for pre-health docs) and reconciles the subprocess's `meta.checks.bpb` against the run's on-pod eval BPB (`db.get_eval_bpb_near`, tolerance `DIAG_BPB_TOL`) into `meta.checks.bpb_match`. The off-pod BPB replicates `train_gpt.eval_val`'s exact byte accounting (`stages_forward.py`) so it's directly comparable.
- The diagnostics package imports the model architecture (`train_gpt`/`config_gpt`) from the gpt-golf checkout — a bare state_dict doesn't define the model, and that model changes constantly, so it's single-sourced in gpt-golf. The package must run under an env that has torch + the val shard/tokenizer (gpt-golf's). `DEVICE=cpu` runs weights-only (forward/token stages skipped); a GPU runs the full suite. Knobs: `DIAG_ENABLED`, `GPT_GOLF_DIR`, `DIAG_PYTHON`, `DIAG_DEVICE`, `DIAG_MAX_BATCHES`/`DIAG_ENTROPY_BATCHES`/`DIAG_SAMPLE_TOKENS`, `DIAG_CACHE_VAL_SHARD` (see `.env.example`).
- Every diagnostics run first ensures the run's val shard + tokenizer are cached locally via `snapshots._ensure_val_shard` — it shells out to gpt-golf's downloader (`data/cached_challenge_fineweb.py --train-shards 0`), which materializes just the val split + tokenizer into gpt-golf's data dir (where `load_validation_tokens()` reads) and no-ops once present. It runs for weights-only (CPU) runs too, not just GPU/token ones, because importing `train_gpt` loads the tokenizer at import time (`config_gpt` builds the SentencePiece processor in `DataConfig.__post_init__`) — so the tokenizer is a hard prerequisite for the subprocess to even start; the val `.bin` files are the extra bit the token stages need. Serialized + memoized per variant; if it fails, token stages degrade to weights-only. Disable with `DIAG_CACHE_VAL_SHARD=0` when the data is provisioned out-of-band.
- UI: the live dashboard (static/js/live.js) is slimmed to a few operational cards plus one **Model Health** verdict card (click-scrolls to the panel; reads `state.diagnostic`). The **Model Health** panel (static/js/diagnostics.js) fetches `GET /api/runs/{id}/diagnostics` (history) and refreshes on the `diagnostic` SSE event, rendering the producer's `health.headline` (threshold-coloured, no JS substring matching), a clickable status timeline, and per-section/per-block drill-down with trend-vs-previous. The **Compare** tab (static/js/compare.js) adds a Model Health diff (verdict + headline side-by-side + per-block movers from `compare.diff_docs`, surfaced via `POST /api/compare`'s `diagnostics` block), a final-loss regression banner, and step/progress chart alignment.
- The `snapshot` event is part of the shared schema — keep it in sync with the gpt-golf producer (`train_gpt.save_snapshot`); the moved diagnostics package's tests live in `tests/` (`uv run --with pytest pytest`).
